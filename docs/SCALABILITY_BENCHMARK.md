# Clinical RAG Scalability & Multi-Tier Benchmarking Architecture

## 1. System Overview & Objective
This document details the multi-scale performance, memory footprint, and latency profile of the Clinical Decision Support RAG system across expanding corpus tiers (236, 311, 1,000, and 5,000 chunks).

---

## 2. Component-Level Explainability Matrix (WHAT / WHY / INPUT / OUTPUT / WHERE / COST / FAILURE / EXAMPLE)

### Stage 1: Dense Retrieval (FAISS InnerProduct)
- **WHAT**: Performs dense vector semantic search over 384-dimensional unit-normalized embeddings.
- **WHY**: Captures clinical synonymy and intent even when exact terminology differs (e.g. "renal failure" matching "eGFR < 30 mL/min").
- **INPUT**: 384-dimensional query embedding (unit L2-normalized) generated by `BAAI/bge-small-en` with prefix `"Represent this sentence for searching relevant passages: "`.
- **OUTPUT**: Ranked array of chunk indices with cosine similarity scores in range `[-1.0, 1.0]`.
- **WHERE**: [`rag_module/indexing/faiss_indexer.py`](file:///e:/Major%20Project%20Code/rag_module/indexing/faiss_indexer.py) (`FAISSIndexer.search`).
- **COST**: Memory: $O(N \times d \times 4\text{ bytes})$; Query Compute: $O(N \cdot d)$ inner products. For $N=5,000$, FAISS search executes in under 2.5ms on CPU.
- **FAILURE**: If index file is corrupt or dimension mismatches ($d \neq 384$), raises `ValueError` on startup and prevents silent ungrounded inference.
- **EXAMPLE**: Query `"Metformin kidney danger"` returns `dailymed_060d40e4-b778-43d9-9596-f9478f773489_contraindications-c0` with dense score `0.9096`.

---

### Stage 2: Sparse Lexical Retrieval (BM25Okapi)
- **WHAT**: Executes term-frequency inverse-document-frequency ranking with document length normalization ($k_1=1.5, b=0.75$).
- **WHY**: Guarantees exact keyword matching for specific drug brand names, dosages, and alphanumeric identifiers (e.g., "500 mg", "eGFR").
- **INPUT**: Tokenized query string (lowercased alphanumeric tokens).
- **OUTPUT**: Ranked array of chunk indices with unbounded positive BM25 scores.
- **WHERE**: [`rag_module/indexing/faiss_indexer.py`](file:///e:/Major%20Project%20Code/rag_module/indexing/faiss_indexer.py) (`FAISSIndexer._init_bm25`).
- **COST**: Memory: Inverted index dictionary $O(\text{vocabulary} + \text{postings})$; Query Compute: $O(\sum_{t \in Q} |\text{postings}(t)|)$. Query time < 1.8ms on CPU.
- **FAILURE**: If BM25 pickle is missing, system falls back safely to pure dense retrieval with audit logging.
- **EXAMPLE**: Query `"Metformin"` yields BM25 score `6.1741` for chunk containing `"Drug: Metformin\nSection: Contraindications"`.

---

### Stage 3: Hybrid Fusion (Reciprocal Rank Fusion - RRF)
- **WHAT**: Non-parametric fusion algorithm combining dense and sparse rank lists using formula:
  $$RRF\_Score(d) = \sum_{m \in \{\text{dense}, \text{bm25}\}} \frac{1}{k + rank_m(d)} \quad (k=60)$$
- **WHY**: Eliminates calibration errors caused by adding unbounded BM25 scores directly to bounded cosine similarities.
- **INPUT**: Ranked list from dense retrieval (top 20) and ranked list from BM25 (top 20).
- **OUTPUT**: Unified candidate list of top 10 unique documents ranked by RRF score.
- **WHERE**: [`rag_module/retrieval/hybrid_search.py`](file:///e:/Major%20Project%20Code/rag_module/retrieval/hybrid_search.py) (`HybridSearcher._reciprocal_rank_fusion`).
- **COST**: Compute: $O(K \log K)$ sorting where $K \le 40$. Latency < 0.1ms.
- **FAILURE**: If one modality fails, RRF gracefully ranks available candidates from the surviving modality.
- **EXAMPLE**: A chunk ranked #1 in dense ($1/(60+1) = 0.01639$) and #1 in BM25 ($1/(60+1) = 0.01639$) receives composite score $0.03278$.

---

### Stage 4: Cross-Encoder Neural Reranker
- **WHAT**: Deep transformer cross-attention model (`cross-encoder/ms-marco-MiniLM-L-6-v2`) scoring (Query, Passage) pairs simultaneously.
- **WHY**: Overcomes bi-encoder representation bottleneck by computing full token-to-token cross-attention interactions.
- **INPUT**: List of `(query_text, chunk_text)` tuples for the top 10 RRF candidates.
- **OUTPUT**: Cross-encoder logit scores (typically range `[-12.0, +12.0]`).
- **WHERE**: [`rag_module/retrieval/hybrid_search.py`](file:///e:/Major%20Project%20Code/rag_module/retrieval/hybrid_search.py) (`HybridSearcher._rerank_candidates`).
- **COST**: Compute: 10 forward passes through a 6-layer MiniLM transformer. CPU latency: ~40–70ms total per query.
- **FAILURE**: If model weights cannot be loaded, pipeline falls back to top RRF candidates with a warning.
- **EXAMPLE**: For query `"What are the contraindications for Metformin?"`, reranker assigns logit `+6.7963` to Contraindications section and `-1.2932` to generic Precautions.

---

### Stage 5: Evidence & Grounding Policy Engine
- **WHAT**: Validates retrieved evidence provenance and verifies that clinical claims are backed by authorized sources.
- **WHY**: Prevents clinical hallucination, blocks synthetic/unverified sources, and refuses out-of-domain or fabricated drug names.
- **INPUT**: Top ranked evidence passages with their complete metadata (`source_id`, `publisher`, `provenance_status`, `source_url`).
- **OUTPUT**: `GroundingResult(is_grounded, accepted_evidence_ids, reason_codes, safety_status)`.
- **WHERE**: [`rag_module/safety/evidence_policy.py`](file:///e:/Major%20Project%20Code/rag_module/safety/evidence_policy.py) (`EvidencePolicyEngine.evaluate_evidence`).
- **COST**: Negligible CPU compute ($O(K)$ regex and dictionary checks, < 0.2ms).
- **FAILURE**: Fails closed (`is_grounded = False`, `accepted_evidence_ids = []`) whenever minimum evidence thresholds are not satisfied.
- **EXAMPLE**: Non-existent drug query `"Cardioregulin contraindications"` results in `status="insufficient_evidence"`, `accepted_chunk_ids=[]`, blocking generation.

## 4. Latency Breakdown Analysis

Where does computational time actually go?
- **Dense Embedding Generation (Query)**: ~15–25 ms (single sentence encoding on CPU).
- **FAISS InnerProduct Search**: ~0.8–2.5 ms (sub-millisecond across all tiers).
- **BM25 Inverted Index Search**: ~0.5–1.8 ms.
- **RRF Merge**: ~0.05 ms.
- **Cross-Encoder Reranking (10 pairs)**: ~50–70 ms.
- **Total Retrieval + Policy Latency (Warm)**: ~65–85 ms.
- **First Query Cold-Start / Model Initialization**: ~350–500 ms (one-time weight load).

### Architectural Conclusion:
Scaling from 236 to 5,000 chunks increases retrieval search time by less than 3 ms. The dominant latency cost is constant with respect to corpus size because the Cross-Encoder only reranks a fixed budget of top-$K$ ($K=10$) RRF candidates.
